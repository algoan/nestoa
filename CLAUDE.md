# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**nestoa** is a deterministic, static OpenAPI 3.1 generator for NestJS / TypeScript codebases. It parses TypeScript source with the swc parser (no compilation, no runtime, no reflection) and emits an `openapi.json`/`.yaml` document. The design goal is CI/CD-friendly reproducibility — it is intentionally *not* runtime-pluggable; customization happens via config or one-file source changes.

The Rust analyser lives in `crates/nestoa`. It is distributed on npm as [`nestoa`](npm/nestoa) via prebuilt platform-specific optional dependencies.

## Commands

Run all `cargo` commands from the repo root.

```sh
cargo build --release                 # build the optimized binary -> target/release/nestoa
cargo build                           # debug build -> target/debug/nestoa
cargo test                            # run all tests
cargo test --package nestoa jsdoc     # run tests in one module (e.g. jsdoc / routes)
cargo test test_name                  # run a single test by name

./target/release/nestoa <project>     # analyse a project dir (defaults to ".")
./target/release/nestoa . -o spec.yaml   # YAML output
./target/release/nestoa . --print-config # print resolved config and exit
./target/release/nestoa . --openapi-version 3.0.3   # emit a 3.0.3 document
./target/release/nestoa . --strict       # exit 1 on any warning or x-unresolved type
```

Tests are inline `#[cfg(test)] mod tests` blocks (in `routes.rs`, `jsdoc.rs`, `schema.rs`, `config.rs`, `interceptors.rs`, etc.), not a separate `tests/` directory.

To exercise the npm shim against a built binary without publishing:

```sh
NESTOA_BINARY=$PWD/target/debug/nestoa node npm/nestoa/bin/nestoa.js . -o /tmp/out.json
```

## Architecture

The pipeline is a straight line orchestrated in `crates/nestoa/src/main.rs`; each stage is one module:

1. **`config.rs`** — loads `nestoa.config.{json,yaml,yml}` from the project root (or `--config`). Defines `include`/`exclude` globs, `output`, `openapiVersion`, `basePath`, `detectGlobalPrefix`, `info`, `resolvePackages`, `resolveTsconfigPaths`/`tsconfig`, `passthroughTypes`, `decoratorAliases`, and `interceptors`. A relative `output` in the config is resolved against the analysed project dir (not the process CWD), so `nestoa services/foo` always writes `services/foo/openapi.yaml`; the `--config` and `-o` flags are paths relative to the CWD, like any CLI argument, and a `--config` that doesn't exist is an error.
2. **`discover.rs`** — walks `include` paths (walkdir + globset) collecting `.ts`, `.tsx`, `.mts` and `.cts` files.
   - **`globalprefix.rs`** — reads the bootstrap file (`main.ts` first, among the discovered files only, never a workspace lib) into a `Bootstrap`: the global prefix from `app.setGlobalPrefix(...)` (string literal, local string `const`, or `node-config-ts` member resolved against `config/default.json`) and the routes its `exclude` option leaves unprefixed (`'health'`, `{ path, method: RequestMethod.GET }`, a trailing `(.*)`/`*` wildcard), plus `app.enableVersioning(...)` when it is URI versioning (its `prefix`, default `v`, and `defaultVersion`). `routes.rs` gives each handler the versions of its `@Version(...)`, else its `@Controller({ version })`, else `defaultVersion`, each adding a `v<N>` segment after the global prefix (`VERSION_NEUTRAL` adds none). The prefix fills `basePath` when it is unset and `detectGlobalPrefix` is on; an explicit `basePath` always wins, and then `exclude` is ignored. `detectGlobalPrefix` only governs the prefix: versioning is always read.
   - **`tsconfig.rs`** — reads `compilerOptions.paths` from the project's `tsconfig.json` (following `extends` — a path, a package such as `@tsconfig/node20`, or a TS 5 array, later entries overriding earlier ones — to the config that declares them; JSONC comments and trailing commas are tolerated) and resolves alias patterns (incl. a single `*` wildcard) to in-repo files under the inherited `baseUrl`, or the declaring config's directory without one. As in TypeScript, an exact pattern wins over a wildcard, the longest wildcard prefix wins among those, and only the winning pattern's targets are tried; `best_match` implements that rule and is shared with package.json `exports`/`typesVersions` resolution in `symbols.rs`. This is how workspace-package imports like `@algoan/core` → `libs/core/src` resolve in an Nx/pnpm monorepo.
3. **`parse.rs`** — swc-backed parser; `.d.ts`/`.d.mts`/`.d.cts` files are parsed in declaration mode. `ParsingContext` owns the shared `source_map`. Each `ParsedFile` carries a `DocComments` index (`jsdoc.rs`) built from swc's comments: every comment is keyed by the position of the first non-whitespace byte after it, so a node's JSDoc is the nearest `/** */` block in the run of comments directly before its span start (a plain or `//` comment in between is skipped, as in TypeScript). A top-level declaration's span leaves out its `export` keyword and class decorators, so the index also maps its start back to them. Each `ParsedFile` also keeps swc's `SourceFile`, whose text `schema.rs` slices for `x-unresolved` source excerpts.
4. **`symbols.rs`** — `Project` builds a cross-file symbol table of every exported class/interface/type-alias/enum, resolving `import`, `export *`, `export * as Ns` (namespaces), barrel files, tsconfig path aliases, and node_modules package declarations so types can be looked up across modules. `resolve_namespace_member` handles namespace-qualified types like `Enums.AccountType`, where the namespace is a module (`import * as`, `export * as`) or a TypeScript `namespace` block, nested ones included; `resolve` accepts the dotted name too. Same-named interfaces in one file merge into one `Symbol::Interface`. A module's `export default …` / `export = …` is recorded as its `default` export, which default imports follow. A name looked up from an importer only sees what the module exports (a declaration file exports everything), so a local declaration never shadows an `export *` re-export. Every lookup goes through the project's `Resolver`, which memoises relative targets, tsconfig aliases, `node_modules` package directories and package entry points, since the same modules are imported from many files and each lookup otherwise stats candidates and re-reads a `package.json`.
5. **`routes.rs`** — `Extractor` finds `@Controller` classes (`export default` ones included), walks their methods and those inherited up the `extends` chain (a redeclared method shadows the base one) for HTTP-verb decorators (`@Get`/`@Post`/…/`@All`; with several stacked, the topmost wins, as in NestJS) and `@HttpCode` (a numeric literal, a named `const` such as `@HttpCode(MULTI_STATUS)` resolved across modules via `Project::resolve_const_number`, or an enum member). Controller and route paths go through **`constval.rs`**, which statically evaluates string literals, templates, `+`, variables, object-constant properties (`ROUTES.LIST`) and string enum members (`AggregatorAlias.LINXO`) across modules; a path it can't evaluate is a warning and its routes are left out. Each Express path is expanded into OpenAPI paths: an optional parameter (`:id?`, `{/:id}`) gives both variants and a constraint (`:id(\\d+)`) becomes the parameter's `pattern`. Parameters map to their OpenAPI location (`@Param`/`@Query`/`@Body`/`@Headers` + config aliases): an object `@Query()`/`@Param()` gives one parameter per property, `@Headers()` without a name and the `Accept`/`Content-Type`/`Authorization` headers are left out, a name read twice is declared once, and pipes shape the parameter (`DefaultValuePipe` → optional with `default`, `ParseIntPipe`/`ParseFloatPipe`/`ParseBoolPipe`/`ParseUUIDPipe` → wire type). `to_openapi()` assembles the final document.
6. **`schema.rs`** — lowers TypeScript types to JSON Schema. This is the largest module and where most type-handling lives: primitives, arrays, tuples, unions (`anyOf`/merged enums), intersections (`allOf`), utility types (`Promise`/`Observable`/`Partial`/`Pick`/`Omit`/`Record`/etc.), `Exclude`/`Extract` (on the lowered union members; `x-unresolved` when assignability cannot be decided from the schemas), `readonly T[]`, `keyof typeof Enum`, `X['k']`, qualified enum members, `Date`. Reusable named types are collected into `ComponentSchemas` and referenced via `$ref`.
7. **`jsdoc.rs`** — parses leading JSDoc into `summary`/`description`, `@param` descriptions, `@deprecated`, `@internal`/`@private`, and `@route-mapping`. The last lets one method serving several paths (`@Get([':id/incomes', ':id/expenses', …])`) declare a distinct response type per path via a brace-body of `'<path-suffix>': <TypeName>` pairs; `routes.rs` matches each concrete path against the trailing suffix and resolves the named type to a schema, overriding the (necessarily unified) declared return type. This is the source-annotation counterpart to the config-driven per-path `response` override in `interceptors.rs`.
8. **`interceptors.rs`** — applies NestJS interceptor transforms to a route's request/response (called from `routes.rs`). For `@UseInterceptors(...)` it resolves each interceptor class and reads its `implements NestInterceptor<In, Out>` type arguments: the handler's (Promise/Observable-unwrapped) return type is unified against `In` to bind the interceptor's generic params (a minimal `unify` + `TypeEnv` of `name -> (origin_file, TsType)`), then `Out` is lowered as the response schema with those bindings active. Lowering `Out` performs **generic instantiation**: a named reference carrying type arguments (`MultiStatusResponse<Omit<T, 'validity' | 'inserted'>>`) binds the referenced declaration's *own* generic parameters to the (eagerly-lowered) arguments and inlines its body per route — so a nested generic element type resolves to the concrete element and utility types like `Omit` applied to a bound param work. Instantiation is scoped to interceptor lowering (gated on an active `TypeEnv`), so ordinary schema output still `$ref`s generic named types. A generic type whose body reaches itself has no finite inlining, so `SchemaCtx::instantiating` carries the instantiations currently being lowered, outermost first, each identified by its declaration *and* the lowered arguments bound to it. Arguments are lowered in the caller's scope *before* an entry is pushed, so a finite nesting (`Box<Box<T>>`) completes and pops before the outer level pushes and is never mistaken for recursion. Reaching an instantiation already in flight — same declaration, same arguments — is genuine recursion: the reference becomes a `$ref` to a name allocated at that point, built from the instance's own arguments (`TreeNode` + `Project` → `TreeNodeProject`), under which the finished body is registered. The *same declaration with different arguments* is not recursion (`Pair<A>` holding `other: Pair<string>`) and is lowered on its own so it keeps its own binding; only a polymorphically recursive type (`Nest<T>` holding `Nest<Nest<T>>`) produces a fresh binding at every level and would never stop, so past `MAX_INSTANTIATION_DEPTH` levels of one declaration the expansion folds back onto the outermost instance in flight. `ComponentSchemas::instantiated` records each finished instantiation against that same key: it keeps `TreeNode<Project>` and `TreeNode<Widget>` apart, and — since a `SchemaCtx` is built per interceptor rewrite — lets a later route binding the same arguments reuse the component instead of lowering a near-duplicate. A declaration nothing refers back to is still inlined whole and never named. The motivating cases are `@algoan/nestjs-pagination`'s `PaginationBodyInterceptor<T>` (`DataToPaginate<T>` → `PaginatedData<T>`) and `@algoan/multi-status`'s `MultiStatusInterceptor<T>` (`T[]` → `MultiStatusResponse<Omit<T, …>>`). Request-body reshaping (e.g. single-or-array) is *not* in the type signature, so it comes from config instead.
9. **`dialect.rs`** — when `openapiVersion` is `3.0.3`, rewrites the finished document's 3.1-only constructs in one pass (called at the end of `routes::to_openapi`, so it also covers schemas supplied verbatim via `interceptors[].response.schema`): `type: [T, "null"]` → `type: T` + `nullable: true`, a `null` `enum` member → `nullable: true`, a `{"type": "null"}` union branch dropped (unwrapping a union that only existed to carry it, and rewriting the member it folds up), a standalone `type: "null"` degraded to an unconstrained schema, a genuine multi-type array split into an `anyOf` of one-type branches, `const` rewritten as a single-value `enum`, and a closed tuple (`prefixItems` + `items: false`, the only shape the analyser emits) merged into a homogeneous `items` capped by `maxItems` — an open tuple is passed through untouched rather than approximated, and `minItems` is never synthesized since `prefixItems` does not require its positions. The nullable-union, standalone-null and tuple conversions lose information, unavoidably — `nullable` is meaningless without a sibling `type`, so 3.0.3 can express neither a nullable `$ref` nor a null-only schema, and its arrays have no per-position types. The walk is over the raw document rather than the OpenAPI object model (so it holds wherever a schema appears), and skips instance-valued keywords — `example`, `examples`, `default`, `enum`/`const` contents, `x-` extensions — so a documented payload shaped like a schema is never rewritten — in keyword position only, since inside `properties` (and the other name-keyed maps) the same word is a field name whose schema must still be walked. Default is `3.1.0`, where the pass never runs.

Key cross-cutting behaviors:

- **Unresolvable types** (typically from `node_modules`) are emitted as `x-unresolved: <TypeName>` rather than silently becoming `{}`, so gaps are visible. Type forms nestoa does not lower (mapped, conditional, `typeof`, other `keyof`, …) are marked the same way, with their source text.
- **Diagnostics.** Every warning goes through `diag::warn`, which records it; `--strict` writes the output, lists each `x-unresolved` by JSON pointer, then exits 1 if there was any warning or unresolved type. Tests read the recorded warnings with `diag::take_warnings`.
- **Output dialect.** The analyser always lowers into JSON Schema 2020-12 (3.1). Most of that output reads identically under 3.0, and `schema.rs` keeps it that way: `ref_to_allof` (called from `attach_doc_to_map`, and only when a sibling is actually being added) rewrites `{$ref}` to `allOf: [{$ref}]` before hanging `description`/`deprecated`/`example` off it, since 3.0's JSON Reference semantics ignore every sibling of a `$ref`; and union members with no wire representation (`void`/`undefined`/`never`, which `keyword_schema` lowers to a JSON `null`) are filtered out of unions rather than emitted as a `null` branch — a `T | undefined` property is already expressed by its absence from `required`. **Nullability and tuples are the two constructs that cannot be spelled the same way in both versions**, so a 3.1 document is never also a valid 3.0 one: `make_nullable` encodes `| null` the 2020-12 way (widen a string/array `type`, add `null` to an `enum`'s values, append a `{"type": "null"}` branch to an `anyOf` (or a verbatim `oneOf`), or wrap a `$ref`/`allOf`/`x-unresolved` in `anyOf: [<schema>, {"type": "null"}]`; an empty `any`/`unknown` schema is left alone), and a tuple lowers to `prefixItems` + `items: false`. 3.0 has neither a `"null"` type nor tuples — see `dialect.rs` below for the downgrade and what it costs.
- **`resolvePackages`** is a glob allowlist of npm package names (e.g. `["@algoan/*"]`) whose TypeScript declarations should be parsed so their exported types resolve to real schemas instead of `x-unresolved`. After discovery, `main.rs::expand_packages` walks the import graph and transitively parses the `.d.ts` entry points of matching packages (resolved via `package.json` `exports`/`typesVersions`/`typings`/`main`, with TypeScript's extension substitution: a `.js`/`.mjs`/`.cjs` target or import specifier stands for its `.ts`/`.d.ts`, `.mts`/`.d.mts` or `.cts`/`.d.cts` file) plus the relative files they re-export. The same pass always runs, so a relative import of a file outside `include` (`../../libs/dto`) is parsed too; route extraction is restricted to the originally-discovered `entry_files`, so pulled-in files can never introduce phantom routes. Empty by default (no third-party inlining unless opted in). Class `extends` and interface `extends` are both lowered to `allOf` so inherited DTO fields are preserved.
- **`resolveTsconfigPaths`** (default true) turns on tsconfig `paths` alias resolution (see `tsconfig.rs`). `tsconfig` optionally points at a specific config file. Aliased + node_modules type resolution share one transitive `expand_packages` pass: it follows relative re-exports, `export * as` namespace targets, tsconfig aliases, and allowlisted packages, pulling each into the symbol table. Use `resolvePackages` for *published* node_modules packages (e.g. a standalone service that `npm install`s `@algoan/aggregator-raw-data`); tsconfig paths cover *workspace* libs that map to in-repo `libs/*/src` (e.g. the backend monorepo, where the same `@algoan/*` names are NOT in node_modules). Most monorepo services need both: `paths` for workspace libs, `resolvePackages: ["@algoan/*"]` for the genuinely-external `@algoan/nestjs-*` packages.
- **`passthroughTypes`** is a list of generic wrapper type names lowered to their first type argument, discarding the wrapper — the config-driven extension of the built-in passthrough set (`Promise`, `Observable`, `Partial`, …) handled in `schema.rs`. Use it for library/project wrappers whose API surface is just the type they wrap, e.g. mongoose's `PopulatedDoc<T>` (`T | RawId`), so a field typed `PopulatedDoc<Metadata>` resolves to `Metadata` instead of `x-unresolved`.
- **`decoratorAliases`** maps a project-specific decorator name to one of the built-in handler kinds (`body`, `query`, `param`, `header`, `user`, `ignore`) — this is the main extension lever and avoids forking the analyser for custom decorators.
- **`interceptors`** is a config map keyed by interceptor class name (as written in `@UseInterceptors(...)`). The response transform is normally inferred from the interceptor's `NestInterceptor<In, Out>` types (see `interceptors.rs`); this map adds `ignore: true` for pure side-effect interceptors (logging/tracing/scrubbing), `requestBody: "single-or-array"` for body reshaping the type signature can't express, and `response: { whenPathEndsWith, schema }` for interceptors whose wire shape is runtime control flow rather than a type. The interceptor's generic `Out` wrapper (e.g. `PaginatedData<T>`) is *inlined* per route rather than emitted as a shared `$ref` component, so different element types don't collide. The `response` override supplies an OpenAPI schema verbatim, optionally gated on a path suffix so sibling routes sharing one interceptor via an array path (`@Get([':id', ':id/jws'])`) keep their distinct shapes — the motivating case is `SignResponseInterceptor`, which only JWS-signs the body when the URL ends in `/jws` (analysis-manager). The override is applied per-path in `routes.rs` (`response_override` in `interceptors.rs`) and wins over the type-inferred `Out`.

- **`errorResponses`** (`errors.rs`) reconstructs the `400`/`401`/`403`/`404`/`409`/`413`/`422` responses NestJS produces but that never appear in a handler's return type. It runs in two tiers. **Tier A** is auto-emitted from route metadata `routes.rs` already has: `401` for guarded routes (config `auth: global | per-controller | none`, minus an `authOptOut` decorator like `@Unprotected`), `403` when a `roleDecorators` decorator (`@Roles`) is present, `400` when a `@Body` DTO is present and `validation` is on, and a per-pipe status for pipes on `@Param`/`@Query` (`pipes` map — the `@algoan` `ParseObjectIdPipe`/`ParseDatePipe` throw `404`, not `400`). One more auto-source sits between the tiers: when `scanThrows` is on (default), each handler's own body is scanned for `throw new <HttpException>(...)` and the matching status is added (e.g. a controller-level `throw new UnprocessableEntityException()` → `422`); only the handler body is read, never called services. **Tier B** is for errors thrown deep in *service* code that no controller-level analysis can see: the `@throws <status> [desc]` JSDoc tag (`jsdoc.rs`) and config `routes[].add` (per path/suffix, optionally per `method`) / `global` (filter-level codes like `413`). Configured paths are full paths, global prefix included, and may use Express `:id` segments; a rule that matches no route is a warning. Every error response `$ref`s one shared literal `Error` component (`{ code, message, status }` — the shape emitted by `@algoan`'s global `HttpExceptionFilter`, not Nest's stock `{ statusCode, message, error }`). `500` is intentionally never emitted by default (a processing failure, not a documented outcome). `routes.rs::extract_class` gathers the AST signals into `errors::RouteSignals`; `errors::compute` does the pure mapping to a `status -> description` map, deduped by status.

When adding a new utility-type lowering, edit `schema.rs`; a new JSDoc tag, `jsdoc.rs`; a new HTTP decorator or param kind, `routes.rs`; an interceptor transform or `unify` case, `interceptors.rs`; an error-response source or status mapping, `errors.rs` (signals gathered in `routes.rs`); a new module-resolution scheme (alias/package/namespace), `symbols.rs` (+ `tsconfig.rs` for path aliases); a 3.0.3 downgrade rule, `dialect.rs`. The code is organized so each is a single-file change.

## npm distribution (`npm/`)

`nestoa` (the published package) ships only the JS shim. `install.js` (postinstall) detects platform/arch/libc, resolves the matching `@nestoa/<tag>` optional dependency, and copies its binary into `bin/`. `bin/nestoa.js` execs that binary, with a runtime fallback that walks the optional deps (in case `--ignore-scripts` skipped postinstall) and a `NESTOA_BINARY` env override. `build-platform-packages.js` is the CI helper that produces each `@nestoa/<tag>` package per target. All packages publish at the same version.

## `codebase/`

Real NestJS projects (`backend` monorepo, `analysis-manager`, `connect-backend`, `console-backend`, `session-manager`, `openapi-v2`) used as **input fixtures** to validate nestoa against actual code. They are not part of the tool. The `backend` monorepo is the eventual integration target (nestoa will run in its GitHub Actions); the standalone services will be migrated into it.
